What the rules mean

Policy v1 is a proposed contrast, not a validated ground truth. The 50-minute threshold and coverage-loss cutoff borrow from calculate_silver_labels.py. Binary familiarity, end-time and date checks follow the priorities in llm/prompts/general_guidance.py. It is deliberately not an exact reproduction of the silver-label policy.

R1 checks individual lost high-priority clients, not just a net count. R2 checks added qualification mismatches and high-priority end-time shortfalls. R3 flags familiarity loss, long commutes and added time/date shortfalls. R4 accepts the remaining cases provisionally. Other tradeoffs, including a single medium/low-priority coverage loss, do not independently trigger rejection.

What this demo can establish

These three examples were deliberately selected to illustrate different mechanisms, including disagreement and agreement. They do not measure accuracy or establish which approach is better. Rule changes are sensitivity experiments; they do not change the cached LLM prompt or evidence.

Only total assignment counts describe the whole plan. Other metrics describe removed/added assignments. End-time coverage is not full-day feasibility: start times and other solver constraints are outside this view. Names are used as keys because the LLM tables contain names; a production adapter should use stable IDs.

Implementation boundary

evaluate_diff.py currently calls statistics summary, assignment summary and assessment models. This standalone prototype replaces all three with engine.js → evaluateDiff(diff, policy). The optimizer and production API are unchanged. The engine reads only the diff, never the cached assessment. Unsupported or inconsistent input returns “manual review”.
